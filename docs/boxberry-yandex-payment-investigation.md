# Krepfield исправление оплаты при получении в Боксберри и Яндекс Доставке

По состоянию на 6 ноября 2026 года подтверждена ошибка передачи оплаты из krepfield.ru в Боксберри/Яндекс: оплаченный на сайте заказ может быть создан у перевозчика с полной суммой к получению. Причина — порядок сохранения статуса и признака оплаты при взаимодействии PayKeeper и модуля доставки. Для исправления рекомендован перенос автоматической выгрузки в код проекта с оценкой 3–5 часов. Реализация пока не начата.

## Проблема и подтверждение

Покупатель выбирает доставку Боксберри/Яндекс и оплачивает заказ на сайте. В личном кабинете перевозчика появляется опция «Оплата при получении», хотя магазин не предлагает такой способ расчёта.

Заказ №1619 специально создан для воспроизведения ошибки. Это тестовый заказ; исправлять его заявку не требуется.

Профили Boxberry «Самовывоз с оплатой при получении» и «Курьером с оплатой при получении» отключены. Активны профили с оплатой на сайте: boxberry:PVZ_COD и boxberry:KD_COD. Платёжная система «Наличными» отключена; активны оплата картами, счёт и внутренний счёт.

Суффикс _COD в этой версии модуля обозначает профиль с оплатой на сайте — это подтверждается его языковыми файлами.

## Причина ошибки

1. PayKeeper получает уведомление об успешном платеже.

2. В processRequest обработчик устанавливает STATUS_ID = PD и вызывает сохранение заказа до завершения обработки оплаты платёжной подсистемой.

3. Модуль Boxberry реагирует на сохранение заказа в статусе PD и запускает создание заявки.

4. При повторном чтении заказа через CSaleOrder::GetByID признак оплаты ещё не отражает завершённый платёж. Метод getPaymentSum возвращает полную сумму заказа.

5. API создаёт заявку с наложенным платежом.

6. После сохранения оплаты последующие выгрузки передают ноль, но повторяют создание заявки с тем же номером. API отклоняет их, поэтому первоначальная сумма к получению сохраняется.

| Запрос по №1619 | payment_sum | Ответ API |
| --- | --- | --- |
| Первый | 222,31 ₽ | Создана заявка с треком YA6AEDCEE3909B7C7CF |
| Второй | 222,31 ₽ | Номер заказа в ИМ уже занят |
| Третий | 0 ₽ | Номер заказа в ИМ уже занят |
| Четвёртый | 0 ₽ | Номер заказа в ИМ уже занят |

Ошибка подтверждается исходящими запросами, а не только отображением в кабинете перевозчика. Статус «Оплачен» и признак PAYED — разные данные; одного статуса недостаточно для безопасной выгрузки.

## Точки в коде для исправления

| Файл на сервере | Роль |
| --- | --- |
| /bitrix/modules/sale/handlers/paysystem/paykeeper/handler.php | processRequest сохраняет статус после оплаты до завершения обработки платежа; ключевой участок около строк 1217–1219 |
| /bitrix/modules/up.boxberrydelivery/classes/general/delivery_boxberry.php | orderCreate запускает выгрузку по статусу; около строк 673–686. Обработчик подключён к OnOrderSave |
| /bitrix/modules/up.boxberrydelivery/classes/general/boxberry.php | GetFullOrderData читает заказ; getPaymentSum определяет сумму к получению по PAYED либо настройке профиля; около строк 567–581 |
| /bitrix/modules/up.boxberrydelivery/classes/general/boxberry_parsel.php | parselCreate формирует payment_sum и вызывает создание заявки |
| /bitrix/cache/log/boxberrydelivery.log | Журнал фактически отправленных запросов и ответов API |

Дополнительный дефект: при включении BB_PAYMENT_AS_PROFILE_TYPE метод ищет _COD в аргументе, который вызывающий код передаёт как DELIVERY_ID. В текущей конфигурации это числовой ID 6 или 7, а не код профиля. Включение этой настройки без исправления преобразования ID в код не является надёжным решением.

## Варианты исправления

| Вариант | Содержание | Оценка и ограничения |
| --- | --- | --- |
| 1. Исправить сторонний модуль | Добавить проверку сохранённой оплаты и существующей заявки в текущую автоматическую выгрузку | Отдельная оценка не согласовывалась. Изменения внутри модуля могут затереться обновлением |
| 2. Перенести запуск выгрузки в код проекта | Отключить штатную автоматическую выгрузку, после сохранения оплаты использовать существующий модуль для создания заявки | Рекомендован. Уточнённая оценка 3–5 часов |
| 3. Перейти на актуальный модуль Яндекса | Выбрать и настроить новый модуль, проверить совместимость с изменённым оформлением заказа и перенести интеграцию | Предварительно 12–20 часов. При существенной адаптации оформления оценка уточняется до переноса |

На время исправления возможна ручная выгрузка после проверки оплаты. Отключение автоматической выгрузки требует изменения фактической настройки статуса PD; одного BB_PARSELCREATE = N недостаточно, поскольку сейчас выгрузку запускает отдельная настройка статуса.

## План варианта 2

1. Сохранить исходные настройки и подготовить изменение в коде проекта под Git.

2. Отключить запуск штатной выгрузки при статусе PD и проверить, что другие штатные автоматические пути создания заявки выключены.

3. Подключить обработку после сохранения подтверждённой полной оплаты. Конкретное событие Битрикса выбрать с проверкой порядка сохранения; непосредственная отправка до фиксации оплаты не допускается.

4. Перед отправкой проверить оплату, отмену заказа, принадлежность доставки к Boxberry и наличие существующей заявки. Защитить создание от повторных уведомлений, рекурсивных сохранений и одновременных вызовов.

5. Для поддерживаемых предоплатных способов передавать нулевую сумму к получению. Проверить полный запрос, включая delivery_sum, чтобы не возникло повторного взыскания доставки.

6. Зафиксировать результат или ошибку создания заявки. При ошибке не отмечать заявку как успешно созданную; предусмотреть понятный ручной повтор после проверки кабинета перевозчика.

7. Проверить сценарии, выложить изменение и проконтролировать реальную заявку.

Отдельная очередь отправки, автоматические повторы и специальный интерфейс обработки ошибок в оценку 3–5 часов не входят. Неопределённый результат запроса, например тайм-аут после отправки, требует проверки существования заявки перед повтором.

## Оценка трудозатрат

| Работа | Вариант 2 | Вариант 3 |
| --- | --- | --- |
| Реализация и настройка | 1,5–2,5 ч | 5–8 ч |
| Проверка оплаты и повторных событий | 1–1,5 ч | 3–5 ч |
| Оформление заказа, ПВЗ, тарифы и доставка | В рамках проверки существующей интеграции | 3–5 ч |
| Выкладка и контроль | 0,5–1 ч | 1–2 ч |
| Итого | 3–5 ч | 12–20 ч |

Оценка варианта 2 учитывает уже выполненную диагностику и использование существующего модуля. Первоначальная оценка 6–10 часов заменена на 3–5 часов после уточнения объёма: расширенная очередь и интерфейс повторной обработки исключены.

Оценка варианта 3 предварительная и не включает возможную стоимость лицензии. Объём зависит от выбранного модуля и совместимости с текущим оформлением заказа.

## Критерии приёмки варианта 2

- Неоплаченный заказ не создаёт заявку автоматически.

- После полной оплаты картой создаётся одна заявка с нулевой суммой к получению.

- Для оплаты по счёту заявка создаётся после фиксации полной оплаты в Битриксе.

- Частичная оплата не запускает выгрузку.

- Повторное уведомление PayKeeper и последующие сохранения заказа не создают дубль.

- Обмен с 1С не создаёт повторную заявку и не запускает отправку отменённого или неоплаченного заказа.

- Сохранение трек-номера не вызывает повторное создание заявки.

- При ошибке API сохраняется диагностируемый результат; ручной повтор учитывает возможную уже созданную заявку.

- В кабинете перевозчика тестовая заявка соответствует предоплате, включая доставку.

- Проверены активные профили ПВЗ и курьерской доставки.

Выкладка включает сохранение прежних значений настроек и возможность отключить новый обработчик. При откате автоматическую выгрузку по статусу PD нельзя возвращать без учёта воспроизводимой ошибки.

## Документация и статус работ

[Документация Битрикса по событиям сохранения и оплаты](https://dev.1c-bitrix.ru/api_d7/bitrix/sale/events/order_special.php) описывает OnSaleOrderPaid как событие изменения признака оплаты при сохранении. При реализации требуется проверить момент фиксации данных и повторные вызовы на установленной версии.

[Страница установленного модуля up.boxberrydelivery](https://marketplace.1c-bitrix.ru/solutions/up.boxberrydelivery/) на момент проверки сообщает, что модуль снят с публикации.

[Актуальная инструкция Яндекса](https://yandex.ru/support/delivery-profile/ru/modules/yd-module-instruction) описывает другой модуль с отдельным определением предоплатных и постоплатных платёжных систем. Она служит ориентиром для варианта 3; её настройки нельзя напрямую переносить на up.boxberrydelivery.

Диагностика завершена. Рабочий код, настройки интеграций и заявка тестового заказа №1619 не изменены; временные серверные диагностические файлы удалены. Пользователь принял уточнённую оценку варианта 2 для документирования; поручения начать реализацию или заменить модуль пока не было. Учётные данные, API-токены и персональные данные покупателей в документ не включены.

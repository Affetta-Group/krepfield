# Переключение автоматического создания заявок Boxberry

По состоянию на 10 ноября 2026 года доработка выложена, флаг **true**: новый контур включён. Новый заказ №1624 выгружен автоматически, в запросе payment_sum=0; клиент подтвердил корректный результат. Ручной запуск для №1624 не выполнялся.

## Состав

- `local/php_interface/boxberry-export-config.php`: единственный флаг; текущая зафиксированная конфигурация — `return true;`. Первая выкладка выполнялась с `false`. При установке на другое окружение начинать с `false`.
- `local/php_interface/lib/BoxberryExport.php`: переключение штатного обработчика и создание после сохранённой полной оплаты.
- `local/php_interface/init.php`: подключение класса и регистрация.
- `tests/boxberry-export-test.php`: проверки логики без Битрикса, сети, заказов и реальных отправлений.

Файлы PayKeeper/Boxberry и настройки автоматизации Boxberry не меняются. Общая диагностика проекта не входит в этот выпуск.

## Режимы

`false`: для обычных заказов вызывается существующий `CDeliveryBoxberry::orderCreate()` с исходными аргументами и настройками. Дополнительно действует блокировка одновременных вызовов для одного заказа. Заказы, по которым новый контур уже начал отправку, в старое автосоздание не возвращаются.

`true`: сохраняется внутренняя запись Boxberry с ПВЗ, но штатное автосоздание не вызывается. `OnSaleOrderSaved` отмечает затронутый заказ; в конце текущего PHP-запроса обработчик заново проверяет заказ и оплаты через отдельное непостоянное соединение с той же базой. Так незавершённая транзакция PayKeeper не может считаться подтверждённой оплатой. Если оплата не видна в зафиксированных данных, заявки не будет; последующее сохранение оплаченного заказа повторит проверку. Это не фоновая очередь и не автоматический повтор API.

Перед созданием проверяются: полная оплата, сумма оплаченных платежей, отмена, активный профиль Boxberry, существующие треки в модуле/отгрузках, предыдущая попытка и способ вычисления оплаты в модуле. Дополнительно проверяется снимок заказа, который прочитает сам модуль: его PAYED должен быть Y, а getPaymentSum — 0. Несовместимая настройка `BB_PAYMENT_AS_PROFILE_TYPE=Y` блокирует отправку.

Вызов создания остаётся штатным: `CBoxberryParsel::parselCreate()`. Сумма к получению должна быть нулевой; стоимость доставки в `delivery_sum` сохраняется как в модуле. По [инструкции Boxberry](https://storage.yandexcloud.net/boxberrysite-public/doc/%D0%98%D0%BD%D1%81%D1%82%D1%80%D1%83%D0%BA%D1%86%D0%B8%D1%8F%20%D0%BF%D0%BE%20%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%B5%20%D0%B2%20%D0%9B%D0%9A%20account.boxberry.ru%20-%20%D0%9D%D0%BE%D0%B2%D1%8B%D0%B9%20%D0%9B%D0%9A%20%D0%98%D0%9C_0.17.pdf), payment_sum задаёт сумму к получению, delivery_sum — объявленную покупателю стоимость доставки. Для контрольного заказа №1624 корректный результат подтверждён клиентом в действующем сервисе.

## Защита от дублей и ошибок

Для обоих режимов используется один `flock` на заказ; вложенное сохранение из модуля не запускает повторное создание. До сетевого вызова атомарно сохраняется `in_flight`, после него — `created` либо `needs_review`. Любое существующее состояние попытки блокирует новое автоматическое создание, в том числе после выключения флага. Повреждённое состояние или недоступное хранилище также блокирует отправку, не прерывая обработку оплаты.

Состояние находится в `.krepfield-boxberry-export` рядом с корнем сайта, вне его публичного дерева; каталог 0700, файлы состояния 0600. Один файловый lock рассчитан на текущий одиночный сервер; при переезде на несколько узлов механизм нужно пересмотреть. В `events.jsonl` пишутся ID заказа, время и результат, без тела ответа, ключей и данных покупателя.

Маркер `in_flight`/`needs_review` нельзя удалять без проверки кабинета перевозчика: заявка могла создаться до тайм-аута или ошибки сохранения трека. Даже явный отказ API оставляет заказ для ручной проверки; автоматических повторов нет. Ручная кнопка модуля не проходит через новый обработчик, поэтому при неизвестном результате нельзя нажимать её до проверки существующей заявки.

## Выкладка и короткое включение

1. Проверить установленный обработчик, доступность приватного каталога и создание отдельного соединения без изменения заказов.
2. Сохранить текущий серверный `init.php` вне публичного дерева и сравнить с исходной версией Git; при посторонних правках остановить выкладку.
3. Загрузить класс и конфигурацию `false`, затем атомарно обновить `init.php`. Сверить загруженные файлы и проверить страницы/регистрацию обработчиков без создания заказа.
4. В согласованный момент заменить только конфигурацию на `return true;` атомарной загрузкой. Значение фиксируется на начало каждого PHP-запроса; уже исполняющийся запрос завершает работу в своём режиме. Общий lock и проверка трека/состояния защищают пересечение режимов.
5. Оформить новый заказ, проверить отсутствие заявки до оплаты; оплатить, проверить одну заявку, нулевую сумму к получению и трек. Проверить отсутствие дубля при последующем сохранении. №1619 не изменять.
6. По результату оставить `true` либо вернуть `false`. Новые заказы после выключения используют старый контур с известным исходным дефектом; затронутые новым контуром сохраняют защиту.

При откате после первой отправки нужно оставлять класс и его регистрацию: именно они сохраняют защиту при выключенном флаге. Полное удаление кода после активации требует отдельной сверки незавершённых попыток. До первой активации можно восстановить исходный `init.php`.

До обнаружения ошибки кэша выполнены 29 проверок с заглушкой метода создания и 32 проверки с самим `CBoxberryParsel::parselCreate()` из установленной версии 2.2.33. Для второго прогона:

Проверяется формирование запроса настоящим методом модуля, нулевой payment_sum, сохранение delivery_sum, ПВЗ/курьер, сохранение трека и повторное событие. Это не сквозной тест с базой сайта или реальным API.

Перед включением был предложен отдельный тест файловых операций. Его отдельный результат пользователь не присылал. ## Исправление после контрольного заказа №1623

Заказ полностью оплачен, но попытка остановилась на `blocked_vendor_payment_snapshot`; маркера отправки и трека нет. В установленном `CSaleOrder::GetByID` найден кэш `$GLOBALS["SALE_ORDER"]["SALE_ORDER_CACHE_".$ID]`, сохраняющий ранний неоплаченный снимок в пределах запроса PayKeeper. После проверки зафиксированной оплаты добавлено удаление только этого ключа перед повторным чтением модулем. Проверки оплаты, трека и предыдущей попытки сохранены.

Регрессионный тест с ранним PAYED=N в кэше упал до исправления и прошёл после: 34 проверки с заглушкой, 37 с установленным методом формирования заявки. Исправление выложено атомарно одним файлом, флаг true не менялся. При выкладке отправка не запускалась. Затем пользователь явно запустил защищённый обработчик для №1623 через PHP-консоль. Результат 10.11.2026 в 14:36:15 МСК: состояние created, трек YA6AF301AFC03C7A2CB совпал с сохранённым в модуле. Это подтвердило создание заявки, но не автоматический запуск для нового заказа.
